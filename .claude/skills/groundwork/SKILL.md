# 프로젝트 초기 설정

목표: 빈 저장소(또는 거의 빈 저장소)에 **Claude 토큰을 아끼는 개발 환경**을 한 번에 세팅한다.
원칙: 결정적인 작업(lint, 테스트, 빌드, 포맷, 구조 요약)은 스크립트와 CI가 맡고, Claude는 판단이 필요한 일만 한다.

## 0. 사전 확인

- `git status`와 파일 목록으로 저장소 상태를 확인한다.
- 템플릿 저장소에서 만든 저장소인지 확인한다. `.template/MANIFEST`가 있으면 거기 적힌 파일은 템플릿 전용 파일이므로 기존 파일로 보지 않고, 충돌로 묻지도 않는다. 이 파일들은 4단계에서 정리한다.
- 그 밖의 파일이 이미 있으면 덮어쓰지 않는다. 무엇이 있는지 보고하고, 겹치는 파일은 사용자에게 처리 방법을 묻는다.
- 기본 브랜치를 확인하고 작업 브랜치 `setup/initial`을 만든다.

## 1. 인터뷰

진행 규칙:
- 한 번에 질문 하나만 한다. AskUserQuestion을 쓸 수 있으면 쓴다.
- 선택지마다 추천 기본값을 첫 번째에 "(추천)"으로 둔다.
- 앞선 답에서 이미 알 수 있는 질문은 건너뛴다.
- 사용자가 "알아서"라고 하면 추천값으로 정하고 넘어간다.
- 질문은 아래 7개를 넘기지 않는다.

질문:
1. 프로젝트 한 줄 설명과 종류 (웹앱 / API 서버 / CLI / 라이브러리 / 기타)
2. 언어와 프레임워크
3. 패키지 매니저, 테스트·lint·포맷 도구 (스택 관습에 맞는 기본값을 제시)
4. CI 실행 시점: PR + main push (추천) / 모든 push / PR만
5. 배포: 지금은 없음 (추천) / 대상 지정
6. CONTEXT.md 자동 갱신: 예 (추천) / 아니오
7. 지켜야 할 코딩 규칙이나 금지 사항 (없으면 건너뜀)

끝나면 결정 사항을 짧은 표로 보여 주고 "이대로 만들까요?" 하고 한 번만 확인한다.

## 2. 생성물

인터뷰에서 정하지 않은 도구나 의존성은 추가하지 않는다. 최소 구성으로 만든다.

1. **프로젝트 골격**: 스택 초기화와 최소 소스 파일, 검사가 실제로 돌도록 샘플 테스트 1개.
2. **조용한 검사 명령**: 스택 관습에 맞는 이름으로 만든다 (`npm run check`, `make check`, `scripts/check` 등).
   - 순서: 포맷 검사 → lint → 타입 체크(해당 시) → 테스트
   - 성공하면 한 줄만 출력한다.
   - 실패하면 실패 항목, 에러 한 줄, `파일:라인`만 출력한다. 전체 로그는 출력하지 않는다.
   - 경로를 인자로 받으면 관련 테스트만 실행한다.
3. **CONTEXT.md 생성 스크립트** (`scripts/gen-context` 등): LLM 없이 결정적으로 생성한다. 디렉터리 구조, 주요 모듈과 역할, 진입점, 공개 API 목록을 담는다.
4. **CLAUDE.md** (60줄 이하):
   - 프로젝트 개요 2~3줄
   - 작업 시작 시 CONTEXT.md를 먼저 읽고, 저장소 전체 탐색은 필요할 때만 한다
   - 검사는 위의 검사 명령만 쓴다
   - 바뀐 부분과 관련된 테스트만 돌린다. 전체 테스트는 CI가 한다
   - 포맷은 도구에 맡기고 직접 지적하거나 고치지 않는다
   - lock 파일, 생성 코드, 빌드 산출물은 읽지 않는다
   - 인터뷰에서 받은 코딩 규칙
5. **`.github/workflows/ci.yml`**:
   - 트리거는 인터뷰 결과를 따른다
   - `paths-ignore`로 문서만 바뀐 변경(`**/*.md`, `docs/**`)은 건너뛴다. 단 CLAUDE.md, CONTEXT.md 변경도 건너뛰는지 확인한다
   - 의존성 캐시를 쓴다
   - 검사 명령을 그대로 실행한다
   - 실패하면 요약을 `$GITHUB_STEP_SUMMARY`에 남겨 사용자가 몇 줄만 복사할 수 있게 한다
6. **`.github/workflows/context.yml`** (6번 질문이 "예"일 때):
   - main push 시 CONTEXT.md 생성 스크립트를 실행한다
   - 변경이 있을 때만 `[skip ci]`를 붙여 커밋한다
   - `permissions: contents: write`를 명시한다
7. **기타**: `.gitignore`, 포맷 도구 설정 파일.

## 3. 검증

- 검사 명령을 실행해 통과하는지 확인한다. 실패하면 고친 뒤 다시 실행한다.
- CONTEXT.md 생성 스크립트를 실행해 CONTEXT.md를 만든다.
- `actionlint`를 쓸 수 있으면 워크플로 파일을 검사한다. 없으면 YAML 문법만 확인한다.

## 4. 커밋과 PR

- 템플릿에서 만든 저장소라면 커밋 전에 템플릿 전용 파일을 정리한다. `.template/MANIFEST`의 `delete` 항목은 삭제하고, `replace` 항목(README.md)은 이 프로젝트용으로 새로 쓴다. `.claude/skills/groundwork/`은 재실행용으로 남긴다.
- 커밋하고 `setup/initial` 브랜치를 푸시한 뒤 PR을 만든다.
- 워크플로 파일 때문에 푸시가 거부되면 GitHub 권한 문제라고 알린다. 사용자가 GitHub 앱 권한을 확인하거나 워크플로 파일만 직접 추가하도록 안내한다.

## 5. 마무리 보고

짧게 보고한다.
- 만든 파일 목록 (파일마다 한 줄 설명)
- 사용자가 직접 할 일 체크리스트:
  - PR 확인 후 머지
  - Actions 탭에서 첫 실행 성공 확인
  - 필요한 시크릿 등록 (있을 때만, 이름 명시)
  - context 워크플로를 쓰면 Settings → Actions → Workflow permissions에서 쓰기 권한 확인. main에 브랜치 보호가 있으면 자동 커밋이 막힐 수 있음
  - 웹 Claude Code 클라우드 환경 설정 스크립트에 넣을 의존성 설치 명령 (텍스트로 제공)
- CI가 실패하면 Job summary의 에러 몇 줄만 붙여 달라고 안내한다.

## 재실행할 때

이미 설정된 저장소에서 다시 실행하면 인터뷰는 바뀐 항목만 묻는다. 기존 파일은 덮어쓰지 않고 변경할 내용을 diff로 보여 준 뒤 확인을 받고 갱신한다.
